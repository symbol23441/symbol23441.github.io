深入理解 ELF：主流可执行文件格式解析与 xv6 加载源码分析

在不同的操作系统中，可执行文件的格式是不同的。它们都有相同的目标：让操作系统能够识别并加载程序到内存中运行。这些格式虽然不同，但都具备一定的通用结构特性，比如入口地址、程序段、符号信息等。

本文首先概览主流平台的可执行文件格式差异，重点分析 Linux 系统标准的 ELF 格式，详细解析其文件结构及类型，并结合工具演示如何查看 ELF 文件结构内容。最后，通过分析 xv6 操作系统中 ELF 加载的核心源码，深入理解操作系统如何将 ELF 程序从磁盘加载到内存并准备执行，揭示加载器的工作原理。

1、主流可执行文件格式概览

文件格式 所在平台 是否主流 文件扩展名示例
ELF Linux、Android ✅ 无、.so、.o
PE Windows ✅ .exe、.dll
Mach-O macOS、iOS ✅ .app、.dylib
a.out 早期 Unix ❌ 已废弃 a.out

其中，ELF 是 Linux 和许多类 Unix 系统（包括 Android、xv6）的标准可执行文件格式，它也被用来表示目标文件（.o）、共享库（.so）和 core dump。

2、ELF文件结构

部分 谁使用？ 作用简述
ELF Header 所有程序/工具 描述文件整体布局
Program Header Table 加载器（操作系统） 指导操作系统如何加载程序段
Section Header Table 链接器、调试器 描述节的属性和位置，供静态分析使用
Segments 加载器 真正加载到内存的部分
Sections 链接器、调试器 编译/链接过程中的逻辑单位
符号表 / 字符串表等 链接器、调试器 提供符号名与地址的映射关系等信息

ELF Header（文件头）

ELF Header（文件头）位置大小固定，位于文件的起始地址。它包含：

  • 魔数：用于确认这是一个 ELF 文件（特征字节为 0x7F ‘E’ ‘L’ ‘F’）
  • 文件类型：如可执行文件、目标文件、共享对象等
  • 架构类型：例如 x86、ARM、RISC-V 等
  • 程序入口地址：程序开始运行的地址
  • 程序头表偏移：指向 Program Header Table 的位置
  • 节头表偏移：指向 Section Header Table 的位置（可选）
  • 各种表的数量与尺寸信息

作用是：指明整个文件的“总纲”，告诉系统或工具如何解释剩余部分。

Program Header Table（程序头表）

这个表包含多个“程序头”条目，每个条目对应一个段（Segment），这些段是操作系统加载时关注的实体。

每个程序头描述：

  • 一个段在文件中的偏移位置
  • 它应加载到内存的哪个虚拟地址
  • 它在文件中的大小和在内存中的大小
  • 段的类型（是否需要加载、是否可执行等）
  • 访问权限（可读、可写、可执行）

作用是：引导操作系统将程序所需的数据正确加载到内存中。

Section Header Table（节头表）

这个表包含多个“节头”，每个节头描述一个节（Section）。节是链接器和调试器使用的逻辑单位，比如：

  • .text：代码段
  • .data：已初始化数据段
  • .bss：未初始化数据段
  • .symtab：符号表
  • .strtab：字符串表
  • .debug_info：调试信息

每个节头描述：

  • 节的名称（通过字符串表索引）
  • 节在文件中的偏移和大小
  • 节的类型和属性（只读、可执行、对齐等）

作用是：供链接器、调试器、分析工具使用，不直接影响运行时加载。

其余数据区

Segments（程序段）是程序加载器关心的内容，它们由程序头表描述。在实际运行中，操作系统根据段信息将文件中的内容加载到内存的对应位置。如：代码段（可执行）、数据段（可读可写）、堆栈段、共享库段等（动态链接时）。

Sections（节）是编译和链接过程中的组织单位，常见节有：.text（代码段）、.data（保存已初始化的全局/静态变量）、.bss（未初始化变量（文件中不占空间，运行时补零）、.symtab / .strtab（符号表和字符串表）、.rel.text（重定位信息）。

节名称字符串表、符号表、重定位表等，这些是节的一部分或通过节头表引用的数据结构，主要用于：

  • 节名称字符串表：存储所有节名的字符串（节头中的名字是偏移量）
  • 符号表：保存函数、变量的名称、地址、类型、作用域等信息
  • 重定位表：链接时使用，描述符号位置的调整方式

这些结构不用于程序运行，但对链接、调试、反汇编等至关重要。

3、C程序各编译阶段对应文件与 ELF 类型

当我们用 gcc 编译一个 C 程序时，通常只看到最终的可执行文件，其实编译过程分为多个阶段，每个阶段可能生成一个中间文件。

各编译阶段对应文件与 ELF 类型如下：

阶段 文件扩展名 是否是 ELF ELF 类型说明
预处理 .i ❌ 否 普通文本文件，展开宏和头文件后的 C 源码
编译 .s ❌ 否 汇编源代码文件（人类可读的汇编指令）
汇编 .o ✅ 是 ELF Relocatable（可重定位目标文件），等待链接
链接 .out 或自定义名 ✅ 是（默认） ELF Executable（可执行文件），类型为 ET_EXEC 或 ET_DYN

从汇编阶段开始，生成的 .o 文件即是标准的 ELF 文件，类型为 ET_REL（可重定位文件）。链接之后的可执行文件（如默认的 a.out 或指定的 main）也是 ELF 文件，类型为 ET_EXEC 或现代系统中的 ET_DYN（PIE 方式）。

在 ELF 文件的结构中，有一个字段叫 e_type，用于标识文件的具体类型。常见类型如下：

类型代号 类型名称 用途说明
ET_REL Relocatable .o 文件，尚未链接，等待组合成可执行文件
ET_EXEC Executable 链接完成的可执行文件，如 a.out、main 等
ET_DYN Shared Object 动态链接库，如 .so 文件或 PIE 格式主程序
ET_CORE Core Dump 程序崩溃后生成的内存转储文件

（2）readelf 详解（最推荐)

readelf 是专门查看 ELF 文件结构的工具，功能丰富而直观。

readelf -a hello查看所有信息（相当于全展开）

此外, -h 仅查看查看 ELF 文件头（ELF Header），-l查看程序头（Program Headers），-S查看节头（Section Headers），-s 查看符号表，-x .text查看指定节的十六进制内容。

（3）objdump 详解（适合反汇编）

objdump 是 GNU 工具集中的反汇编分析工具，可以查看代码内容、段、符号等。

命令 说明
objdump -d hello 反汇编 .text 可执行段
objdump -x hello 查看 ELF 头、段、节等
objdump -t hello 符号表（类似 nm）
objdump -s -j .data helo 查看 .data 节的原始内容

5、xv6 操作系统加载ELF可执行文件源码

5.1 ELF结构体定义

elf.h这里仅定义了操作系统加载程序需要的结构，ELF Header和 Program Header。未定义链接等所需的section头和段结构。

5.2 ELF可执行程序加载

在 xv6 中，用户程序的加载由 exec.c 中的 exec(char *path, char **argv) 函数完成。它负责将一个 ELF 格式的可执行文件加载到当前进程的内存空间中，并准备好进入用户态运行。

这种加载机制体现了一个最简化的操作系统加载器工作流程：从磁盘读取→解析结构→映射内存→加载内容→准备执行环境。它仅使用 ELF 的 Program Header，不依赖 Section Header，符合现代操作系统运行时加载的通用做法。
